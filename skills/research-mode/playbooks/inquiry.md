### Inquiry

Phase: any. First used in explore: the thinking before and between searches; in design it runs on one experiment (see below). Turn what the user already knows, what the lab's `wiki/` holds from past experiments, and what the user read in Zotero into a good set of questions, extend them, and hand the ones that need searching to **Literature review**. Talk first; search later.

**Before any search (the first round).**
- **A. Wiki.** If `wiki/` exists, read `wiki/CLAUDE.md` and follow its router for the project's methods and past analyses. This is the user's own experience: label it `[user]` or `[studies]` as the wiki marks it, never as published evidence. Say in `inquiry.md` what the lab already knows, so the search does not repeat it.
- **B. Interview and brainstorm.** Run `interrogate` in interview mode on the aims (the interview in `docs/inputs/` to `02_aims-and-milestones.md`) and use `brainstorming` moves (its notes go to `docs/rstack/d-brainstorm/`) to find what is not known yet. Write each gap as a question with what a good answer would be.
- **C. Standard inquiry.** Steps 5 and 6 below turn the list into `inquiry.md` and `inquiry-search.md`. Stop there until **Literature review** returns. Steps 1 to 4 run after the user has read papers.

**In design (one experiment).** Run only A and B on that experiment: the wiki's procedures, equipment and past analyses (`[user]`, never evidence), then interview, `brainstorming` and `interrogate` for what is not known. Write `docs/rstack/d-inquiry/inquiry-<experiment>-wiki.md`: materials, equipment, procedure and open gaps, each with the wiki's source mark. **Experimental design** copies from it; the design note itself carries no wiki link. Steps 1 to 9 do not run.

**Where files go.** All Inquiry files (`inquiry.md`, `inquiry-search.md`, `inquiry-<topic>-wiki.md`, `claims.md`) live in `docs/rstack/d-inquiry/`, never loose in `docs/rstack/`. `check_layout.py` fails on a stray one.

**Understanding ladder.** Every statement in `docs/literature-review/` carries a label and moves up only through review: `[user]` (the user's reading, unverified), `[assistant]` (the assistant's reading, unverified), `[source-checked]` (checked against the paper's text, with cite and page), `[verified: cite]` (confirmed by an external source that passed a cite-check).

1. **Collect.** Run `scripts/inquiry_extract.py <project>`. It adds new question-like annotations (red highlights and comments with a question mark) to `docs/rstack/d-inquiry/inquiry.md` under Open, once each.
2. **Align in your own words.** Per paper and theme, write `docs/literature-review/papers/<cite>/alignment.md`: what the user read (`[user]`, from their colours and comments, verbatim) beside what the paper says on a re-read of the passage the user marked (`[assistant]`, with page). Say it back to the user in your own words and let them correct you.
3. **Interrogate both readings.** Run `interrogate` in interview mode, in short back-and-forth rounds. Test the user's understanding and your own. Classify each item as confirmed, misconception (cite the passage), unknown, or my error. Explain each misconception and unknown in plain words, with the passage, only when the user asks. Use `scientific-critical-thinking` on the assumptions behind each item.
4. **Extend beyond the paper.** Do not stay inside one source. For each theme use `brainstorming` moves (gap, transfer from neighbouring fields, inversion, change of scale or constraint, failure analysis) to add questions the papers do not raise. Pull from the other papers in `references.yaml` too. Mark added questions as proposals.
5. **Write `inquiry.md`.** Group by theme under plain-language headings. Each question: the user's words or the proposed question, where it came from, its class from step 3, and its triage: answered by this paper, answered by another paper, needs search, or for the supervisor. Show it and wait. The user confirms before anything costs time or money.
6. **Send out.** Write the needs-search items to `docs/rstack/d-inquiry/inquiry-search.md` with the questions, the context, and the papers already read. Then run **Literature review**, which runs `/hyperresearch` with the user's go-ahead. Its report is a lead: every claim stays one until a paper the user read confirms it. The user adds chosen papers to Zotero and reads them; snapshot their annotations and repeat from step 1.
7. **Resolve.** When sources return, use `arena` for competing explanations of a mechanism and `interrogate` on the proposed answers. Answer from papers the user has read, with cite and page, and say plainly when the papers do not settle it.
8. **Promote and file.** Put verified material into `docs/literature-review/cross-papers/`, keeping the ladder labels on every statement, and update each paper's `README.md`.
9. **Claims.** Write `docs/rstack/d-inquiry/claims.md`: one line per claim, with branches mechanism, evidence (cite and page), caveat, open question, and a Mermaid mindmap. Claims come only from answered items and from statements at `[source-checked]` or above. The user confirms before they feed `03` to `05`.

**Reply:** misconceptions and unknowns found, questions added, items waiting for search or the supervisor, and the claims proposed.
