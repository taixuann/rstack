### Inquiry

Phase: any (cross-phase). Serves as the project's internal knowledge query and understanding check across every phase: retrieves what the project and lab `wiki/` already hold via `qmd`, aligns and interrogates the user's reading against Zotero papers, and surfaces open gaps for **Literature review** or **Experimental design**. Talk and query locally first; search externally only through **Literature review**.

Specific principles: `principle-sources-not-memory`, `principle-steelman-before-dismissing`, `principle-ask-do-not-fill`. Skills: `qmd`, `interrogate`, `brainstorming`, `arena`, `scientific-critical-thinking`, `sources` (to verify claims against source passages).

**A. Project and wiki memory (`qmd`).** Use `qmd` directly on the project collection (`-c <project>`, covering the whole project except `**/data/**`) and the shared `wiki` collection (`-c wiki`) to retrieve existing notes, methods, and past analyses — no manual browsing through `wiki/CLAUDE.md` or folders unless `qmd` is not installed. Lab and wiki material is the user's own experience: label it `[user]` or `[studies]`, never as published evidence.

**B. Design-time experiment inquiry (in design).** Before **Experimental design**, query `wiki` and the project via `qmd` for procedures, equipment, and past analyses (`[user]`), then run `brainstorming` and `interrogate` (interview mode) for open gaps. Write `docs/inputs/<date>_inquiry_<experiment>-wiki.md` (materials, equipment, procedure, open gaps with wiki source marks). **Experimental design** copies from it; the design note itself carries no wiki link. Steps 1 to 9 below do not run here.

**C. Paper alignment and question log (after reading Zotero papers).** Steps 1 to 9 below align the user's Zotero highlights with the paper text, interrogate both readings, and feed verified statements into `claims.md` (or hand needs-search gaps to **Literature review**).

**Where files go.** The question log and wiki lookups are dated files in `docs/inputs/`: `<date>_inquiry_<about>.md`, front matter kind inquiry, source chat or assistant, `confirmed: no`. A later round is a new dated file, never an edit. Each deep-research brief (`<date>_<about>.md`) lives in `docs/rstack/d-inquiry/`; claims go in `docs/literature-review/claims.md`. Nothing is loose in `docs/rstack/`. `check_layout.py` fails on a stray one.

**Understanding ladder.** Every statement in `docs/literature-review/` carries a label and moves up only through review: `[user]` (the user's reading, unverified), `[assistant]` (the assistant's reading, unverified), `[source-checked]` (checked against the paper's text, with cite and page), `[verified: cite]` (confirmed by an external source that passed a cite-check).

1. **Collect.** Run `scripts/inquiry_extract.py <project>`. It adds new question-like annotations (red highlights and comments with a question mark) to a new `docs/inputs/<today>_inquiry_questions.md`, once each across all inquiry files.
2. **Align in your own words.** Per paper and theme, write `docs/literature-review/papers/<cite>/alignment.md`: what the user read (`[user]`, from their colours and comments, verbatim) beside what the paper says on a re-read of the passage the user marked (`[assistant]`, with page). Say it back to the user in your own words and let them correct you.
3. **Interrogate both readings.** Run `interrogate` in interview mode, in short back-and-forth rounds. Test the user's understanding and your own. Classify each item as confirmed, misconception (cite the passage), unknown, or my error. Explain each misconception and unknown in plain words, with the passage, only when the user asks. Use `scientific-critical-thinking` on the assumptions behind each item.
4. **Extend beyond the paper.** Do not stay inside one source. For each theme use `brainstorming` moves (gap, transfer from neighbouring fields, inversion, change of scale or constraint, failure analysis) to add questions the papers do not raise. Pull from the other papers in `references.yaml` too. Mark added questions as proposals.
5. **Write the question log** (a dated inquiry file in `docs/inputs/`). Group by theme under plain-language headings. Each question: the user's words or the proposed question, where it came from, its class from step 3, and its triage: answered by this paper, answered by another paper, needs search, or for the supervisor. Show it and wait. The user confirms before anything costs time or money.
6. **Send out.** Write the needs-search items to one brief, `docs/rstack/d-inquiry/<date>_<about>.md`, with the questions, the context, and the papers already read. A later search gets its own brief, and each report names its brief in its front matter. Then run **Literature review**, which runs `/hyperresearch` with the user's go-ahead. Its report is a lead: every claim stays one until a paper the user read confirms it. The user adds chosen papers to Zotero and reads them; snapshot their annotations and repeat from step 1.
7. **Resolve.** When sources return, use `arena` for competing explanations of a mechanism and `interrogate` on the proposed answers. Answer from papers the user has read, with cite and page, and say plainly when the papers do not settle it.
8. **Promote and file.** Put verified material into each paper's `README.md` in `docs/literature-review/papers/`, keeping the ladder labels on every statement.
9. **Claims.** Write `docs/literature-review/claims.md`, the one claims file for papers and reports: one line per claim, with its source type (paper or report), with branches mechanism, evidence (cite and page), caveat, open question, and a Mermaid mindmap. Claims come only from answered items and from statements at `[source-checked]` or above. The user confirms before they feed `03` to `05`.

**Reply:** misconceptions and unknowns found, questions added, items waiting for search or the supervisor, and the claims proposed.
