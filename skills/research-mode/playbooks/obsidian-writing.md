### Obsidian writing

State: any. Use whenever you write a note the user reads and comments on in Obsidian: a learning session, a paper README, an alignment, a cross-paper note. Done means the note opens in Obsidian with its figures showing, the user's comments untouched, and `scripts/check_references.py` passes.

The user reads these files beside the paper and comments in them. The file is the conversation, so the chat reply stays short.

1. **Place it.** One home per kind: `docs/literature-review/papers/<cite>/` for one paper, `docs/literature-review/cross-papers/` across papers, `docs/rstack/<state>/` for state documents; small expansions are written inline beside the term; flat, with `parent` and `depth` in front matter; nesting is said by `parent`, never by subfolders), not per paper, `docs/inputs/` for the user's own words. Start the file with front matter: `created`, `updated`, `kind`, `voice`, and `paper` when it belongs to one. Link other files with relative links. Embed pictures with `![[figures/<name>.svg]]` (from a core or branch note, `![[../figures/<name>.svg]]`), with the picture in the `figures/` folder of that area.
2. **Write for a reader who is new.** Short sentences. Define a term where it first appears. Say what a word points at before using it. Label statements with the understanding ladder. Put the user's own words in quote blocks marked `[user]`, copied word for word. Write one flowing account, not boxes: define each term in the sentence where the thing first happens, with its rule or number in the same paragraph. No Definitions or Properties callouts, no list of words before the story.
3. **Draw rarely, in a `mermaid` code block.** One figure per note by default, a second only if words and the first cannot show the structure, never one per step. Obsidian draws it with Pele, in the user's own theme, so write the Mermaid text straight into the note. Pele covers every Mermaid 12.1 diagram type: flowchart, sequence, state, class, ER, Gantt, pie, mindmap, timeline, quadrant, XY chart and more. Keep labels short. A picture Mermaid cannot draw (a cell with ions, a circuit) is an SVG drawn by hand into `figures/` and embedded. Render a hand-drawn SVG to PNG (`rsvg-convert -w 1000 x.svg -o x.png`) and look at it before the user does. To preview a Mermaid diagram, run `node scripts/render_diagram.mjs <diagram.mmd> out.svg` (the vendored Pele in `vendor/pele/`, MIT, Node 20 or newer).
4. **Leave the user's comments alone.** The Document Comments plugin stores a comment as `<!--c:ID-->quoted text<!--/c:ID-->` in the text and a thread block `<!--co:ID by:NAME at:ISO status:open quote:"..."` then one `name (ISO-time): text` line per message, then `-->`. Reply by adding one line `claude (<UTC ISO time>): <text>` before the closing `-->`. Keep it on one line and do not start it with a word followed by a colon. Never resolve, delete, or move a thread. The user edits the file while you work, so read it again before each change and change only the exact lines you mean to. Never rewrite a whole note from memory. Answer threads by hand with the rule above. The Document Comments plugin refuses a new comment when the file changed after the user selected text, so edit a note the user is reading as little as possible: one batched write per turn, appended at the end, with small expansions inline beside the term.
5. **Check.** Run `scripts/check_references.py docs/literature-review/references.yaml`. It fails on missing front matter, a `mermaid` block that does not parse (the vendored Pele checks it), an embed that points at nothing, and unbalanced comment markers, and each error names the fix.
6. **Hand back.** Tell the user the file path and the one thing to read or answer next, in three lines or fewer. Do not restate the note in chat.
